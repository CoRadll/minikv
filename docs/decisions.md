## D-001 源文件强制 UTF-8，MSVC 显式加 `/utf-8`

**背景**：源码含中文注释，文件编码为 UTF-8。

**问题**：MSVC 默认按系统代码页（简体中文环境为 936/GBK）解析源文件。
UTF-8 的中文字节被按 GBK 解码后，若某个字节被解释为行尾反斜杠，会触发行续接，
把下一行声明吞进注释里。表现不是「编码错误」，而是诸如
`error C2039: "kProjectName" 不是 "minikv" 的成员` 的幻影错误，极难定位。

**决定**：CMake 中统一 `add_compile_options(/utf-8)`；编辑器侧固定
`files.encoding = utf8`、关闭 `autoGuessEncoding`。

**后果**：
- 干净构建 0 warning（曾经每条 C4819 都是潜在的数据损坏）
- 跨机器协作不依赖本地代码页，Linux/macOS 下行为一致
- `/utf-8` 同时等价于 `/source-charset:utf-8 /execution-charset:utf-8`，
  不可与二者重复叠加，否则报 `D8016`

## D-002 全项目不使用异常，错误通过 `Status` 返回值传递

**背景**：存储引擎的失败路径很多且必须被处理（IO 失败、CRC 不匹配、文件截断）。

**问题**：异常会隐藏控制流。在「把数据写进文件」这类代码里，
一个未捕获异常跑到析构链里，可能导致半写状态或静默丢数据。

**决定**：
- 所有可能失败的函数返回 `Status`，成功为 `ok()`
- 内存分配失败按致命错误处理，不做逐处捕获
- 不使用 `throw` / `try` / `catch`

**后果**：
- 失败路径在调用处显式可见，编译器也能提醒忽略返回值
- 与 RAII 配合良好：资源释放走析构，错误传播走返回值
- 代价是代码略啰嗦，需要在每层做 `if (!s.ok()) return s;`

**替代方案**：`std::expected`。C++23 才标准化，MSVC 19.34 支持不完整，暂不采用。

## D-003 `include/` 与 `src/` 逐文件同构，`api/` 为公开门面

**背景**：头文件与实现如果自由摆放，项目长大后会出现
「头文件在 A 目录、实现散在 B/C/D」的情况，重构成本极高。

**问题**：如何让「改一个文件」的波及范围可预测。

**决定**：
- 有 `.cc` 的头文件，必须在 `include/minikv/` 下有一条**完全相同的相对路径**
- 纯定义 / 纯虚接口允许只有头文件，登记在例外名单
- 对外门面收敛到 `include/minikv/api/`，内部头不对外承诺稳定

**后果**：
- 找文件只需一次路径映射，重构可批量机械替换
- 规则由 `scripts/check_layout.ps1` 校验，不依赖人工记忆
- 例外需要显式登记，避免「特例悄悄扩散」

## D-004 阶段制推进（S0–S5），按验收标准而非日历排期

**背景**：投入时间不固定，可能出现「一周 20 小时、接下来一周 2 小时」的波动。

**问题**：按周排期会不断过期，且无法判断「做到哪算够」。

**决定**：
- 以「可验收的产出」为阶段边界，每个阶段结束都是可停下的点
- 每个阶段有明确的完成判据（可执行命令 + 预期输出）
- 不设截止日期，只设依赖关系

**后果**：
- 任意阶段暂停都有可交付物，不存在「做到一半什么都没有」
- 里程碑与简历叙事对齐：S2 可写、S3 完整、S5 有量化数据

## D-005 头文件契约分级：契约级 vs 草案级

**背景**：S0-T2 一次性建立了 24 个模块的头文件。其中一部分接口是由数据流倒推的
（例如 Engine::Put 必定调用 WalWriter::Append 与 MemTable::Put），
另一部分是凭经验预判的策略类接口（例如 Compaction::Run()）。

**问题**：如果所有头文件都被当成"已冻结的契约"，等 S3/S4 实现时发现签名不合适，
就会倾向于硬凑实现而不是改接口；如果全部留成空 class，则丢失跨模块依赖的编译期验证。

**决定**：
- 按可信度分两级，并在文件内显式标注
- **契约级**：util/*、wal/*、memtable/memtable.h、pi/*
  由数据流决定，改动需同步上层调用方
- **草案级**：	able/*、db/*、cache/*、memtable/skiplist.h
  文件内标注 `// 草案：<阶段>实现时允许调整接口签名`
- 草案级接口可以自由修改，因为当前没有任何调用者
- 跨模块依赖（如 engine.h 依赖 iterator.h / options.h / status.h）
  在 S0 就通过编译验证，而不是等到实现阶段

**后果**：
- 草案标记让"可改"这件事写在代码里，避免把占位当承诺
- 空 class 方案被否决：它不表达"尚未设计"，只表达"没有任何成员"，
  且会使头文件自包含检查与跨模块依赖检查失效
- 代价是 S3/S4 可能出现"改头文件"的提交，这被视为正常演进而非返工

## D-006 构建脚本纯 ASCII，配 .cmd 包装器

**背景**：scripts/ 下的构建、测试、布局检查脚本面向 Windows 开发者。

**问题**：本机环境同时存在四个约束，任何一个都会让脚本直接失效：

1. 只装了 **Windows PowerShell 5.1**，没有 PowerShell 7
2. PowerShell 5.1 把**无 BOM 的脚本按 ANSI(GBK) 解码**，中文注释被误解码后
   产生语法错误（实测报 `Unexpected token`，报错行号还与实际无关）
3. 默认执行策略是 `Restricted`，`.ps1` 直接调用会被拒绝
4. `.cmd` 里的非 ASCII 文本按 OEM 代码页解释，中英文混排会把命令行拆碎

此外还有两个 API 级差异：`[System.IO.Path]::GetRelativePath` 在 .NET Framework 4.x
不存在；`` 在 `param()` 默认值求值阶段为空。

**决定**：
- 三个 `.ps1` 脚本**全部使用 ASCII**（注释与输出消息均为英文）
- 每个脚本配一个 `.cmd` 包装器，内部用
  `powershell -NoProfile -ExecutionPolicy Bypass -File` 调用，
  因为 `.cmd` 不受 ExecutionPolicy 约束
- 路径相对化手写实现，不依赖 .NET Core API
- `` 的默认值在函数体内解析，不放在 `param()` 里
- 脚本只使用 PowerShell 5.1 兼容语法（`#Requires -Version 5.1`）

**后果**：
- 同一套脚本在 PowerShell 5.1 与 7 上都能跑
- 在默认 `Restricted` 策略的机器上无需改系统设置即可使用
- 代价是脚本内的提示信息为英文；中文说明保留在 README 与本 ADR
- 副作用：后续修改脚本必须重跑一次
  `scripts\check_layout.cmd` 与 `scripts\test.cmd` 验证，因为这类错误
  只在执行时暴露

## D-007 每个阶段交付可执行的 `minikv demo sN` 演示

**背景**：阶段完成后需要向自己、也向评阅者证明"做完了且能用"。单元测试全绿是必要条件，
但它证明的是"我写的断言通过了"，不是"这个部件在真实使用中像样"。

**问题**：三种常见做法都有缺陷。

1. 口头/截图说明：会过期，无法复现
2. 临时写一个 `main.cpp` 打印几行：用完即弃，下个阶段要重写，不构成资产
3. 只靠单元测试：看不到"日志里到底记了什么"、"重启后到底恢复了多少"

**决定**：
- 每个阶段交付一个 `minikv.exe demo sN` 子命令
- 四条硬约束：
  1. **确定性输出**：除耗时外文本固定，重复执行逐字节一致
  2. **只用公开接口**：`Engine::Put/Get/Delete` + 直接读文件字节，不碰私有成员
  3. **自带断言**：任一步不符立即 `FAIL` 并以非零码退出
  4. **落盘**：transcript 写入 `demo/sN-transcript.txt`
- 阶段完成判据增加一条：`demo sN` 退出码为 0 且 transcript 已生成
- 详细脚本见 `docs/demo-spec.md`

**后果**：
- 演示同时充当端到端测试，不是额外负担而是回归网的一部分
- 面试可现场执行，30 秒讲清一个阶段的能力，比翻代码有效
- 代价是每阶段增加约 0.5–1 小时（S1 具体为 1 小时）
- 确定性要求会限制某些演示形式（例如不能展示随机耗时分布），
  这类内容归入 S5 的 benchmark，不进 transcript

## D-008 测试临时目录可配置，并提供三级回退

**背景**：测试需要创建临时目录写入文件，且不能污染仓库。

**问题**：最初实现只调用 `std::filesystem::temp_directory_path()` 并忽略错误码，
在受限环境（受限令牌、安全软件按进程拦截）下会静默失败，测试报出
"exists() 为 false"这种看不出原因的断言失败。实测该环境下：

- `%TEMP%` 的 ACL 允许当前用户完全控制
- PowerShell 手工 `New-Item` 可以创建目录
- 但测试可执行文件写入同一路径返回 `ERROR_ACCESS_DENIED`，只能写工作区内

**决定**：
- 临时目录按三级优先级选择：`MINIKV_TEST_TMPDIR` → 系统临时目录 → 当前工作目录
- 每次降级都打 `WARN` 日志并说明原因
- `TempDir` 暴露 `ok()` 与 `error()`，测试失败时把原因写进断言信息
- 仓库内 `.minikv-test-tmp/` 加入 `.gitignore`
- 受限环境下把 `MINIKV_TEST_TMPDIR` 指向**工作区内**的可写目录

**后果**：
- 测试在受限环境与普通环境都能跑，且失败时能立刻看出是环境问题还是代码问题
- 后续阶段（S2 写 SSTable、S5 崩溃测试）的数据目录同样要放在工作区内，
  演示脚本统一使用 `demo-data/` 相对路径
- 代价是多了一层配置，且有环境相关的行为差异

## D-009 文件系统 API 的两个平台陷阱

**背景**：`util/env` 封装目录操作，需要同时在 Windows 与 POSIX 上语义一致。

**问题**：实现过程中撞到两个 Windows 特有的坑。

1. **`DeleteFile` 是 Windows 宏**。`windows.h` 会把 `DeleteFile` 定义成
   `DeleteFileW`/`DeleteFileA`。在含 `windows.h` 的翻译单元里，函数**定义**
   被宏改名，而其他翻译单元看到的仍是 `DeleteFile`，最终表现为
   `LNK2019: 无法解析的外部符号 minikv::DeleteFile`——声明明明存在，链接却找不到。
2. **目录刷盘不可行**。对目录句柄调用 `FlushFileBuffers` 通常返回
   `ERROR_ACCESS_DENIED`，NTFS 不支持这种用法。

**决定**：
- API 改名为 `RemoveFile`，从源头避开宏冲突；头文件里注明原因
- `SyncDir` 在 Windows 上尽力而为：打不开或不支持时记 DEBUG 并返回 OK，
  不让上层失败；目录项的一致性改由 `RenameFile` 的
  `MOVEFILE_WRITE_THROUGH` 保证
- POSIX 侧保持标准语义：`open(dir, O_RDONLY|O_DIRECTORY)` + `fsync`

**后果**：
- 公共接口不依赖平台头文件是否被包含，任何顺序包含都不会冲突
- Windows 上的“目录已落盘”是弱保证（与 SQLite 等项目的取舍一致），
  文档中已写明；需要强一致时依赖重命名的写入穿透语义
- 排查时间成本很高（LNK2019 与声明无关），值得记录

## D-010 WAL 恢复语义：一律截断到最后一条完整记录

**背景**：回放 WAL 时可能遇到无法完整解码的记录——通常是「写了一半就断电」。

**问题**：没有额外的校验链，就无法可靠区分两种情形：

1. **尾部写了一半**：应该丢弃，数据本身是安全的
2. **中段被外部篡改/损坏**：丢弃之后的数据意味着真实的数据丢失

日志记录之间没有长度索引或分段 checksum，一段坏字节之后可能恰好是「看起来合法」的记录，
因此无法从字节本身判断损坏发生在尾部还是中段。

**决定**：
- 回放遇到第一条无法解码的记录就**停止**
- 把文件**截断**到最后一个完整记录的结束位置，并 `fsync`
- 丢弃的字节数通过 `WalReader::dropped_bytes()` 暴露，同时打一条 `WARN`
- 回放本身返回成功（不把「尾部有残记录」当成错误）
- 崩溃测试只验证「已 `Append` 返回成功的记录必须可恢复」，不承诺未完成写入的保留

**后果**：
- 启动永远不会因为尾部残记录而失败，符合「先能起来」的工程直觉
- 代价：中段真实损坏会被当成尾部处理，表现为静默丢弃后续数据；
  缓解手段是 `dropped_bytes()` 与 `WARN` 日志，不静默
- 若将来需要精确区分，可以引入分段文件（segment + 段尾 CRC），
  但那会把 WAL 轮转的复杂度提前到 S1，因此暂不采用
